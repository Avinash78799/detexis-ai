# Local-only HTTPS workspace

Prepared on 15 November 2026 after the owner chose local computer hosting without
a domain. Disposable Linux CI at commit `3a69f146` passed CA/hostname verification,
HTTPS account registration/session cookies, the authenticated coverage page and
manifest, no-store, CSRF/origin refusals and refusal by a client without the CA.
No host trust was installed by CI. The owner subsequently activated Windows
hosting, imported the reviewed root and reported warning-free Chrome access.
Signed-in automated browser acceptance remains incomplete; this is not a public address.

Shield keeps its HTTPS Origin checks and Secure, HttpOnly, SameSite cookies.
The optional Caddy proxy provides `https://localhost:8443`, with a private local
certificate authority. Only IPv4 and IPv6 loopback (`127.0.0.1:8443` and
`[::1]:8443`) are published; there is no public tunnel, DNS purchase, router
forwarding, database exposure or automatic change to Windows/browser trust.
The proxy has no database credentials, Docker socket or host trust-store mount.
Use the `localhost` URL: raw-IP HTTPS failed in the current Python-client check
and is not an accepted alternative. No certificate-warning bypass is required.

An IPv4-only binding caused roughly 2.1-second cold `localhost` HTTP-client
connections on the owner machine. In a disposable proxy, adding IPv6 loopback
reduced four simultaneous cold readiness requests to 50–54 ms with CA/hostname
verification retained. This diagnostic is not deployed-load or browser evidence.
The startup helper validates both requested Docker bindings and actual published
ports, refusing wildcards, missing loopbacks, duplicate addresses and unexpected
ports. A running proxy can retain requested bindings after a failed allocation
without publishing any listener; configured bindings alone are insufficient.

## Start the prepared proxy

The reviewed PowerShell helper starts only the optional proxy and exports its
public root, without installing trust:

```powershell
./tools/start_local_https.ps1 -CertificateDirectory C:\PRIVATE\ShieldCertificates
```

Replace that output directory with a folder you control. The helper has run on
Windows and exported the same public-root fingerprint after the IPv6 update.
The owner imported the reviewed certificate and reports warning-free Chrome
access. The new actual-port guard also passes the Windows regression cases;
it does not install certificate trust or establish signed-in browser acceptance.

For manual startup, from this directory after the computer instance is healthy:

```powershell
docker compose -p detexis-shield-computer --env-file .computer.env -f docker-compose.yml -f docker-compose.computer.yml -f docker-compose.malware.yml -f docker-compose.local-tls.yml --profile localtls up -d --no-build --no-deps localproxy
```

This may pull the pinned official Caddy image. Keep the existing .computer.env
and volumes. Do not run `down -v`, change the database password or start the
public production proxy. If port 8443 is occupied, inspect the owner of that port
before making changes. No browser credentials should be entered before trust is
configured and a warning-free HTTPS page is verified.

## Review the public root certificate

Export only the public certificate into a private folder you control:

```powershell
docker cp detexis-shield-computer-localproxy-1:/data/caddy/pki/authorities/local/root.crt C:\PRIVATE\shield-local-root.crt
certutil -dump C:\PRIVATE\shield-local-root.crt
certutil -hashfile C:\PRIVATE\shield-local-root.crt SHA256
```

The directory is a placeholder; choose an existing folder. Confirm the named
authority is the one generated by this instance. Record its SHA-256 fingerprint
before proceeding. Never export or share `root.key`, intermediate keys or the
private Caddy data volume. Those keys can issue certificates trusted by clients
that install this root.

## User-controlled certificate trust

Installing a root changes which TLS certificates your Windows account trusts.
Only install the public root generated by your own local instance after reviewing
it and approving that change. The configuration uses `skip_install_trust`, so
starting the proxy does not install a root on the host automatically.

After explicit approval, you can import that exact public certificate using the
Windows certificate wizard, choosing **Current User**, then **Trusted Root
Certification Authorities**. Keep the certificate fingerprint and name for
future removal. Never bypass a browser certificate warning to enter credentials.
If the in-app browser does not use that trust store, use a browser that does or
configure its trust separately; do not disable certificate verification.

Then visit `https://localhost:8443/ready` and confirm `{"ok":true}` with no
certificate warning. Open `/app`, create your own account and privately save its
one-use recovery code. Synthetic account/browser testing requires approval for
this local origin separately from any previous public origin.

## Persistence, stop and removal

The local CA persists in `detexis-shield-computer_local_tls_data`; certificate
renewal needs that volume and a running proxy. `python tools/computer.py start --local-https` explicitly starts the optional
proxy on later application updates. Plain `start` does not activate an inactive
proxy. `computer.py status` includes optional/stopped services and `stop` includes
the proxy while retaining its CA volume.
Docker restart policy cannot start Windows/Docker or prevent sleep.

Stop only the optional proxy using the same Compose files and `stop localproxy`.
Existing API and datastore containers can remain running. To stop using the CA,
remove only its recorded certificate from Current User's root store using the
Windows certificate manager. Keep other trusted roots unchanged. Removing trust
causes local HTTPS warnings until this instance's root is trusted again.

This address is for this computer. A sensor on another computer cannot use its
own `localhost` to reach Shield. Network/public hosting and real remote-site
onboarding remain separate work. Use the included persistent Python demo on the
same computer for the first local installation check; synthetic use is not
real-user adoption.
