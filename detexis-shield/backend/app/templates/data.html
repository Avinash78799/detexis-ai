Understand what leaves your site.

The implemented defaults and controls in this Shield build. Read this before connecting real traffic.

Request telemetry

The Python sensor sends request method, path, a redacted query string, user agent, response status, elapsed time, detection flags and numeric features. IP addresses are hashed using a private site salt and the current day before transmission. Raw request bodies, cookies and authorization headers are not collected by this SDK.

Named password/token fields are redacted, but this is not a guarantee that all personal data is removed. Paths, user agents and unrecognized query fields can contain personal data or secrets. Salted hashes are identifiers, not a promise of anonymity. Review the routes and traffic you intend to monitor and only connect sites you own or have permission to monitor.

Accounts and access

Shield stores the account email, password hash, recovery-code verifier, session verifiers and expiry times, site hostnames, API-key verifiers and domain-verification state. Passwords use Argon2id. Recovery codes, browser session tokens and sensor keys are stored as verifiers rather than their original values. New sensor keys and recovery codes are displayed once.

The sign-in session uses a Secure, HttpOnly, SameSite cookie. The interface does not keep authentication tokens in browser local storage. Account emails are sign-in identifiers; mailbox ownership is not verified in the current sender-free setup.

Owner sessions scope dashboard and inbox access to that owner's websites. A sensor key also grants access to its site's monitoring API and legacy dashboard, so treat it as a private credential. Revoking a key stops its future authenticated requests; it does not delete data already collected. Changing a password signs out old browser sessions and leaves separately managed sensor keys in place.

Findings, scans and notifications

Rules and optional locally loaded ML artifacts process telemetry into findings, hourly baselines and incidents. Review decisions and notes are retained with incident history. Domain scans only run after ownership verification, and store check results and scores.

In-app incidents work without an email sender. External email, Slack or Telegram delivery is optional and requires an operator-configured destination. Configured channels receive incident details; ask the operator which channels are enabled for your site. This build does not send request content to an LLM service.

Retention and removal

Maintenance defaults to 30-day telemetry retention, configurable by the operator with a minimum of seven days. Request events expire by server receipt time; incidents and their review history expire after their last-seen time. Scan results and hourly buckets also expire. Cleanup runs periodically and depends on a healthy maintenance process.

Expired browser sessions are removed by maintenance. Account, website and key records do not currently have an automatic expiry or a self-service deletion/export action. Removal requests require the deployment operator. Backups have a separate retention policy; deleting live records does not remove existing backup copies.

Check the deployment you use

The Shield operator controls hosting, database access, backups, configured retention, notification destinations and operational logs. HTTPS infrastructure and hosting providers can receive network metadata such as connection IP addresses independently of the sensor's IP hashing.

Before relying on a hosted service, obtain the operator's contact details, actual retention and backup policy, and the process for data access or removal. A temporary computer-hosted Cloudflare tunnel is a development demonstration; its availability and URL are not persistent hosting.
